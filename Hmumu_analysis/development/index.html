    Development¶

    How the pieces fit¶

    hmumu (tools/hmumu.py)                     one entry point, one implementation per job
 ├─ skim      campaigns/skim.sh ─> htcondor/condorsubmit.py ─> htcondor/run_skim.sh ─> analysis/skim.py
 ├─ validate  campaigns/workflow.py:validation_command ─> htcondor/submit_datasets.sh ─> analysis/validate_dataset.py
 ├─ hist      campaigns/workflow.py ─> htcondor/submit_datasets.sh ─> htcondor/run_stage_condor.sh ─> histograms/hist_maker.py
 │            hadd:  histograms/hadd_hists_to_processes.py
 │            merges: hmumu merge-systematics / merge-eras (common/merge_era_templates.py)
 │            plot:  plotting_tools/plot_all_regions.sh ─> plotting_tools/hist_plotter.py
 ├─ dy-weights campaigns/workflow.py (dy_weights) ─> tools/derive_dy_*.py
 ├─ combine   combine/build_signal_extended_datacards.py, combine/run_signal_extended_fits.sh
 ├─ chain     campaigns/chain.py (runs the commands above in order)
 └─ status    campaigns/status.py
    • Physics: analysis/ (skim selection), corrections/ (corrections and their variations, C++ headers), common/ (prepare_rdf, variables in add_vars.py, weights in apply_custom_weights.py, DNN inference in dnn_application.py), histograms/hist_maker.py, config/Run3_*/.
    • Orchestration: campaigns/, htcondor/, tools/hmumu.py. Condor jobs run the code of the checkout that submitted them, live: do not edit a checkout while its jobs run.
    • Paths: only in config/paths.yaml, read with common.paths.path(key) in Python and $HMUMU_<KEY> in shell.

    Tests¶

    source env.sh
python3 -m pytest -q tests studies

    The tests need the CMSSW environment (ROOT, correctionlib) but no EOS access. Some compile snippets of the C++ headers (corrections/jets.h, analysis/AnalysisTools.h) and run them on synthetic events, so they follow the production code.

    Changing the analysis¶

    A variable: define the column in common/add_vars.py (or where its inputs are built), add its binning to config/plot/histograms.yaml, list it in variables of config/<era>/maincfg.yaml to have it in all_variables. ./hmumu where <column> shows where a column is defined, configured and used; ./hmumu vars <substring> lists the defined columns.

    A selection, region or category: config/<era>/selections.yaml, one per era. Regions and categories with store: True are the ones campaigns produce with --regions all/--categories all.

    A systematic: its variation in corrections/ or as a weight, its entry in config/<era>/systematics.yaml with the nuisance name and cross-era correlation (SYSTEMATIC_CORRELATIONS.md), and, if it is a new family, the family in SYSTEMATICS of the campaign configs.

    A campaign: a new config/campaigns/<name>.sh (see the README); ./hmumu hist <name> paths checks it. A variant of an existing campaign can source it and override a few variables, as dnn_vbf_dy_unweighted.sh does.

    Before merging a change to physics code, produce the same small histogram request with the old and the new code and compare them bin by bin:

    python3 histograms/hist_maker.py --era Run3_2025 --dataset VBFHto2Mu_M125_powheg \
    --input-manifest "$HMUMU_MANIFESTS/Run3_2025/VBFHto2Mu_M125_powheg.json" \
    --output-file /tmp/$USER/new.root --systematics Central Muon \
    --variables DNN_NNOutput m_mumu --mass-regions Signal_Fit --categories VBF --max-files 4

    Multithreaded RDataFrame sums in a different order at every run: expect relative differences of order 1e-15, identical entries.

    Using the analysis selection in your own code¶

    common.prepare_rdf.prepare_rdf applies the variables, selections and weights of the analysis to a skim, for histograms, tuples or numpy arrays. Call it once per graph, before any action:

    from common.utilities import initialize_root_runtime
from common.prepare_rdf import prepare_rdf

initialize_root_runtime()          # loads analysis/AnalysisTools.h; required when passing rdf=
nodes = prepare_rdf(
    rdf=raw_skim_rdf,              # or input_dir=/input_files=
    dataset_name=dataset_name, era=era, is_data=False,
    selections_cfg=sel_cfg, systematics_cfg=syst_cfg,
    seg_dict=dataset_seg_dict,     # normalisation of the WHOLE dataset, also for a subset of files
    enable_dy012j=True, enable_dyptll=True, enable_dynjets=True,
    split_jet_multiplicity=True,
    additional_cuts=None,          # e.g. the GenVBFFilter cut of the 105-160 DY halves
)
inclusive = nodes["inclusive"]

    The result is an ordered dict: inclusive first, then the ggF 0J/1J/≥2J and VBF Hard/PU components (exclusive within their selection; the DY_inclusive_* views are sums of components, not to be added again). Data return only inclusive, empty inputs {}. enable_custom_weights=False drops the three DY reweights and keeps the nominal weights. The DY payloads come from the dataset's reweight_jsons in process_names.yaml unless given explicitly. prepare_region_dataframes builds the region/category/systematic views. additional_cuts from samples.yaml are not applied for you.

    Training tuples from the skims: common/README.md.
